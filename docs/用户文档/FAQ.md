# token-route FAQ

> 按「一般 / 接入 / 运行时 / 运维」四类组织。查不到答案时：消费方先看 [01_消费方接入手册.md](./01_消费方接入手册.md)，管理方看 [02_管理与运维手册.md](./02_管理与运维手册.md)，仍无解提 Issue 并附 `trace_id`。

## 一、一般

**Q1：token-route 和 API 网关是什么关系？会替代网关吗？**
不会，职责正交。网关管南北向流量（用户鉴权、**调用方/用户·key 限流**、路由转发）；token-route 只回答「这次该用哪个**上游**」并做**条目（上游）容量治理**——它不代理任何业务流量，转发仍由你的调用方或网关执行。

**Q2：和 THMP 候选解析是什么关系？**
分层共存：LLM 同步热路径走 THMP 契约（每次调用经 token-route +1 跳不划算）；任务面/调度类中低 QPS 路由走 token-route（亲和/状态机/容量治理刚需场景）。

**Q3：为什么没有管理页面、没有 CRUD 接口？**
设计拍板（零管理写面）：表壳与脚本走 config 种子（改配置 + 滚动重启），条目数据走上游 FEED（改数据 + refresh ping）。服务端只保留只读 ops 查询面用于观测排障。配置变更低频，重启成本可接受，换来的是最小攻击面与单一真源。

**Q4：支持多实例部署吗？一致性怎么保证？**
支持且建议 2 实例。实例无状态（表壳在各自内存来自同一份 config），状态全在 Redis；写路径全 Lua 原子 + 评估器/拉取用 Redisson 锁防多实例重入。不支持 Redis Cluster（Lua 多键跨槽），用主从/哨兵单实例。

**Q5：Redis 挂了会怎样？数据会丢吗？**
resolve 返回 EMPTY（不误动作不 5xx）、report 拒收，**表壳（表定义/脚本）在进程内存不受影响**；恢复后条目数据从上游 FEED 回源自愈（≤60s）。亲和绑定丢失 = 会话下次 resolve 重绑；租约/计数丢失 = 短暂归零放开后自然收敛。表壳与条目各有真源（config / 上游），无可丢数据（运维手册 §5.1）。

**Q6：性能如何？**
resolve P99 ≤ 20ms（表壳内存 + Redis Lua 单往返）；report 批量 ≤100 条 P99 ≤ 30ms。你的调用链增加的延迟 ≈ 一次内网请求。

## 二、接入

**Q7：每次真实调用前都要 resolve 吗？能缓存结果吗？**
要。这是预占直连模式的设计：每次 resolve 现场预占并发位 + 读最新状态/容量，变更下一请求生效。无 SDK 缓存——缓存会吐过期绑定、绕过容量预占，两者都是模式红线。

**Q8：我的场景 QPS 很高，担心延迟，怎么办？**
先归层评审：高 QPS 低延迟热路径不适合本服务（每次 +1 跳且无缓存兜底），这类场景维持现有静态路由/专用链路；中低 QPS 调度/任务类才是目标场景。

**Q9：非 Java 语言怎么接？**
HTTP 直连四个接口即可（任意语言），见接入手册 §5 完整走查；服务交付 OpenAPI 3 机读契约可生成各语言客户端。

**Q10：session_id 必须传吗？**
表开了亲和时必须传（用任务 ID/会话 ID 等业务天然键，≤128 字符）；未开亲和的表传了也会被忽略（返回 affinity=NONE）。

**Q11：biz_params 能传什么？有多大限制？**
≤64 键，值 string/number。传什么取决于你的表配的过滤/选择脚本读了哪些键——接入前向管理方要「参数口径」。

**Q12：data_json 里的字段谁定义？去哪问语义？**
上游系统定义、原样透传（仅 `capacity` 是服务端约定字段）。字段语义找上游供给系统/管理方对齐，token-route 不解释。

**Q13：report 拿到 10700 怎么处理？**
部分成功——只补发 `rejected[]` 里的条目；迟到（超过 lease_ttl）的条目不用补，回收时速率已照计。整批重发会使 accepted 部分 win/fail 双计数。

## 三、运行时

**Q14：resolve 返回 entry_id=null（EMPTY）是出错了吗？**
不是，HTTP 200 code 0 的正常业务分支。按 `reasons` 处置：`ALL_FILTERED` 查参数口径 / `CAPACITY_EXHAUSTED` 退避重试 / `TABLE_EMPTY`、`TABLE_OFFLINE` 找管理方 / `SCRIPT_DEGRADED` 告警管理方（接入手册 §8.2）。

**Q15：为什么反复 resolve 总返回同一个（刚失败的）条目？**
亲和黏着：单次失败后条目仍是 ACTIVE，连败未达脱离阈值（默认 5）。要立刻换条目：`detach` → `resolve`。

**Q16：条目为什么被跳过/冻结了？谁干的？**
三种可能：连败/失败率达标自动降级冻结、某消费方上报了 `DISABLE_FAIL`（立即 FROZEN）、容量满载。ops 面 `GET /v1/ops/state-logs?entry_id=` 可查迁移来源（STATE_MACHINE / REPORT_DISABLE / FEED_STATUS）。

**Q17：怎么立刻解冻一个条目？**
上游在 FEED 响应中显式携带 `"status": "ACTIVE"` + `POST /v1/refresh/{tid}` ping（管理位）；或等 `frozen_until` 窗满惰性回（5min×4ⁿ 封顶 2h）。

**Q18：迟到的 report 会怎样？**
超过 lease_ttl 后租约已被超时回收，report 按非法 lease 拒收（10700 rejected）——无需补偿，回收时速率已按保守照计。

**Q19：告警里的「租约超时回收数」说明什么？**
有消费方 resolve 后没有 report（lease 纪律违规）。这不是 token-route 的故障，是接入质量问题——按 `X-Caller-Id` 归因到具体消费方督促修复。

## 四、运维

**Q20：怎么调整条目权重 / 上下线？**
改**上游** FEED 数据（weight / status 字段）→ `POST /v1/refresh/{tid}` ping（或等 60s 惰性周期）。token-route 无任何写接口，这是全 FEED 模式的边界。

**Q21：怎么建表 / 改策略 / 换脚本？**
改部署配置 `tr.tables` + 滚动重启（脚本文件随部署制品版本化；启动编译 fail-fast，坏配置拒启动）。见配置手册 §3 与运维手册 §1 走查。

**Q22：怎么看实时状态和监控？**
ops 只读面四接口（表/条目状态、决议日志、亲和事件、迁移史，运维手册 §3）+ Prometheus SLI（EMPTY 率 / 刷新失败率 / script_degraded / 租约回收数 / 状态迁移数，运维手册 §5.2）。

**Q23：怎么知道是哪个消费方在调用/违规？**
消费方请求带 `X-Caller-Id` 头（可选、不校验）落决议日志 `[TR-RESOLVE] caller=`；接入清单要求消费方必带，违规归因靠它。
