# 开发原则

> token-route 后端开发的最高纪律。任何编码任务（含 AI 辅助编码）动手前先读本文；本文与其他文档冲突时，以本文为准。
>
> 版本：v1.0（2026-08-31）

适用范围：token-route 服务与 token-route-sdk 的全部后端编码工作。

---

## 原则一：framework4j 优先，禁止重复建设

后端必须基于 framework4j（fwk4j）开发，**不允许绕开框架自建同类能力**。

技术栈基线：Java 17 + Spring Boot 3.5 + fwk4j v1.5.1（web / accesstoken / redis，见 [07_实施计划.md](./07_实施计划.md)）。fwk4j 版本升级跟随其正式发布，不在本项目内魔改依赖。

任何能力（鉴权、web 封装、redis 访问、异常与错误码、结果信封……）动手前先回答一个问题：**framework4j 是否已提供？**

- **已提供** → 直接依赖使用，禁止复写、二次包装、绕行。
- **未提供 / 不能满足需求** → 只允许以下两条通道：

| 通道 | 动作 | 前置条件 |
|---|---|---|
| ① 自行实现 | 在本项目内实现该能力 | **必须先人为确认**（任务说明或评审中记录确认人与结论），不得默认自作主张 |
| ② 提交 issue | 向 framework4j 仓库提交 issue，要求新版本实现 | issue 写清需求场景、期望 API、验收标准 |

两条通道可并用：短期以①保进度（人为确认后），同时以②推动上游收敛；待 fwk4j 新版本发布后，用框架实现替换自实现并回归测试。**禁止的是第三种情况——未确认、未提 issue，悄悄重复造轮子。**

判定流程：

```
新能力需求
  → 查 fwk4j 能力（文档 / 源码 / issue）
      ├─ 已有       → 直依赖使用
      └─ 无/不满足  → 提交任务评审：
            ├─ 人为确认自实现 → 本项目实现（标记待上浮）＋ 同步提 issue
            └─ 不急需        → 提 issue，跟随 fwk4j 版本
```

配套约束：

- 自实现代码须集中、可替换，不与业务代码纠缠，便于后续平移回 fwk4j。
- 已用 fwk4j 能力出现"不够用"时，先看升级版本能否解决，其次才走双通道。
- [01_设计方案.md §8 资产复用清单](./01_设计方案.md)是"复用优先"的既有落点；清单之外的复用机会按同一流程处理。

## 原则二：四方对齐——编码任务的完成定义（DoD）

每个编码任务，**文档、代码、测试、规范四方对齐后，任务才算结束**。缺任何一方 = 任务未完成，不得交付、合入、关闭。

| 方 | 对齐含义 | 典型落点 |
|---|---|---|
| 文档 | 设计 / 契约 / 数据 / 时序与最终实现一致；实现偏离了文档，要么改实现、要么走评审改文档，不留两边各说各话 | [docs/开发文档/](./) 01~08 号文档、docs/用户文档/ |
| 代码 | 实现符合设计文档与接口契约，不夹带契约外行为 | src/ |
| 测试 | 测试与代码、契约一致，覆盖本任务的行为与边界（含异常路径），全量通过 | test/ |
| 规范 | 符合项目编码规范与架构约定：分层与依赖方向、命名、错误码与信封、日志、配置项风格 | 本文 + 各文档中的约定 |

任务收尾自检清单（全部勾选才可结束）：

- [ ] 涉及的接口 / 契约 / 数据结构变更已回写到对应文档
- [ ] 实现与文档逐条对得上（无"文档说了但没做 / 做了但文档没有"）
- [ ] 新增 / 变更行为有对应测试，测试全绿
- [ ] 命名、分层、依赖方向、错误码、配置风格符合既有规范（对照 benefit4j 改造基准）
- [ ] 无违反原则一的自建能力（自实现均有人为确认记录，均有对应 issue）

07_实施计划.md 的各 S 出口闸门，在原有检查项之上叠加本清单。

## 原则三：copy 参考项目再改造，不从 0 开始

后端工程以参考项目为起点：**copy [funcommons/benefit4j](https://github.com/funcommons/benefit4j) 的后端代码，在其上改造出 token-route，禁止从 0 搭建。**

- **动作**：将 benefit4j 后端代码 copy 进本仓 → 按本仓设计文档（[01_设计方案](./01_设计方案.md) / [02_接口契约](./02_接口契约.md) / [03_数据设计](./03_数据设计.md)）改造业务语义。
- **保什么**：工程结构、构建配置、分层惯例、公共封装、测试组织方式——与 benefit4j 保持一致，减少无谓差异。
- **改什么**：业务模型、接口契约、领域逻辑，按 token-route 文档替换。
- **为什么**：骨架已被验证、风格天然对齐、评审聚焦业务改造点，同时是"复用优先"的最大化落点。
- **与原则一的关系**：benefit4j 中与 fwk4j 能力重叠的自建部分，改造时收敛为 fwk4j 直依赖（按原则一流程处理）。
