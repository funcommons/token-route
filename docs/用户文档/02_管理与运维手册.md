# token-route 管理与运维手册

> 适用对象：token-route 运营/运维与路由表管理方。
> **V2.0 零管理写面**：没有任何 admin CRUD 接口——表壳与脚本走 **config 种子**（改配置 + 滚动重启），条目数据走 **FEED 上游**（改数据 + refresh ping）。覆盖：建表走查 / FEED 上游接入 / ops 查询 / 告警排障。

## 1. 场景一：新建路由表（config 种子走查）

1. **写表定义**：在部署配置 `tr.tables` 增一项（完整字段见[配置手册 §3](./配置手册.md)）：

```yaml
tr:
  tables:
    - name: video-task-upstreams        # 即 table_id
      tenant-id: "0"
      strategy-type: WEIGHTED_RANDOM    # 或 ROUND_ROBIN / WEIGHT_FIRST / SCRIPT
      affinity:
        enabled: true
        idle-timeout-seconds: 28800     # 8h
        max-failures: 5
      lease-ttl-seconds: 30
      state-policy: default             # V1 仅 default（窗口制）；channel-legacy 预设 P2
      data-profile: generic
      feed:
        refresh-url: http://task-infra:9200/v1/routes/video-upstreams
        interval-seconds: 60
```

2. **脚本表另备脚本文件**（`SCRIPT` 策略 / 过滤脚本，05 号规格）：

```text
/conf/tr-scripts/llm-selector.groovy      # 选择器：(params, entries) → entry_id
/conf/tr-scripts/tenant-cost-filter.groovy # 过滤：(params, entry) → boolean
```

   脚本随部署制品评审/版本化；**启动编译 fail-fast**——坏脚本 = 拒绝启动并指名表/脚本（10630），不会带病上线；
3. **滚动重启**（实例1 → 健康 → 实例2）；
4. **冒烟**：上游 FEED 就绪后 `POST /v1/refresh/{tid}` 立即拉取 → ops 面核对条目数 → 一次 resolve 验证。

> 调整策略/亲和参数/换脚本 = 同一走查（改配置 + 滚动重启）；运行期无任何配置写接口。

## 2. 场景二：FEED 上游接入（条目数据，唯一写方）

1. **上游实现 GET refresh_url**，返回全量条目（02 §8 契约）：

```json
{ "entries": [ { "name": "channel-a", "weight": 100.0, "order_no": 1,
                 "data_json": { "base_url": "https://up-a.example.com",
                                "capacity": { "max_concurrency": 20, "rate_limit_value": 100, "rate_window_ms": 1000, "rate_unit": "REQUEST" } } } ] }
```

   要点：**全量语义**（缺失的 name 会被移除，其亲和绑定**惰性脱离**——下次 resolve 自然重绑，无需上游关心）；status 只认 ACTIVE/OFFLINE，**缺省保留现值**（不重置状态机判定态）；**显式 ACTIVE = 管理位解冻/上线**（FROZEN 条目逃生通道）；`capacity` 是 token-route 唯一读取的载荷字段（限速/并发治理阈值，不配 = 不启用该维度）；data_json 序列化后 **≤8KB**（超限本次拉取整体拒收 10633）；`entry_id` 由服务端按 hash(table_id, name) 确定性生成（上游无需感知）；
2. **刷新三触发**：惰性（默认 60s 快照龄）/ 上游变更后 ping：

```bash
curl -X POST http://token-route:9302/v1/refresh/video-task-upstreams -H "X-Api-Key: $TR_API_KEY"   # none 模式免头
# → {pulled, upserted, removed, elapsed_ms}；拉取失败保旧值不报错
```

3. **条目上下线/调权重**：改上游 FEED 数据 → ping（或等惰性周期）。无管理接口。

## 3. ops 只读查询面（`/v1/ops/**`，默认 JWT `tr-admin`）

| 接口 | 用途 |
|---|---|
| `GET /v1/ops/tables/{tid}/status` | 表元数据（config 回显）+ 条目实时状态（判定态 / 窗口计数 / **conc_active 并发占用** / **速率桶水位**）+ 活跃亲和数 + **feed 拉取游标（last_pull / fail_count）** |
| `GET /v1/ops/resolve-logs?table_id&from&to&result` | 决议日志（ring 热窗 7 天；全量走结构化日志 → Loki） |
| `GET /v1/ops/affinity-events?table_id&type=BIND\|DETACH` | 亲和事件史 |
| `GET /v1/ops/state-logs?entry_id` | 状态迁移史（from/to/原因/触发方） |

```bash
curl http://token-route:9302/v1/ops/tables/video-task-upstreams/status -H "Authorization: Bearer $JWT"
```

## 4. 鉴权模式配置（无凭证签发/轮换）

两面各一个配置项，切换/轮换 = 改配置滚动重启（无管理接口）：

```yaml
tr:
  auth:
    contract-mode: none    # none / apikey / jwt（生产建议 apikey 或 jwt）
    ops-mode: jwt          # 运维只读面，生产保持 jwt
    api-key: ${TR_API_KEY} # 仅 apikey 模式
```

- **apikey 轮换窗口**：先滚动重启服务端新 key → 通知调用方更新 env → 期间旧 key 401（内网低峰操作）；
- jwt 模式 token 由平台统一认证签发，token-route 只验不签；
- 无 per-消费方凭证：调用方身份靠可选 `X-Caller-Id` 头落日志归因。

## 5. 日常运维

### 5.1 数据可靠性模型（无快照，V2.0）

| 数据 | 真源 | 丢失后果 | 恢复 |
|---|---|---|---|
| 表定义 + 脚本 | config 文件（部署制品） | 无（进程内存持有） | 重启即回 |
| 条目数据 | 上游 refresh_url | Redis 清空 | 下一轮拉取自愈（惰性 ≤60s / ping 即时 / miss 同步回源） |
| 亲和绑定 / 租约 / 计数 / ring 日志 | Redis（可丢失、可接受） | 亲和丢失 = 会话重绑；租约丢失 = 并发归零短暂放开；日志丢 7d 热窗 | 消费方下一请求自然重建 |

> Redis 建议 AOF everysec（副本语义强化）；**无快照导出/重推工具**（表壳与条目各有真源，无可快照对象）。

### 5.2 告警项建议（SLI，01 §9）

| 指标 | 阈值建议 | 含义 |
|---|---|---|
| resolve EMPTY 率 | > 5% 持续 5m | 全过滤/满载/空表/Redis 故障 |
| feed 刷新连续失败 | ≥ 3 次 | 上游 refresh_url 不可达/schema 漂移 |
| `script_degraded_total` 增速 | > 0 持续 | 线上脚本在降级裸奔（选择器回退/过滤失效） |
| 租约超时回收数突增 | — | 消费方漏发 report（lease 纪律违规） |
| 状态迁移数突增 | — | 上游批量故障信号 |
| 401 率（apikey 模式） | 突增 | 调用方 key 未同步轮换 |

### 5.3 排障速查

| 症状 | 看哪 |
|---|---|
| 服务起不来 | 启动日志 10630：脚本编译失败指名表/脚本 → 修脚本文件再滚；10633：config/FEED schema 非法 |
| 消费方拿不到新条目 | 上游改数据后有没有 ping？`GET .../status` 核对条目集；refresh-url 可达性 |
| 条目总是 FROZEN | `status` 里 `consecutive_failures` / `win_failures`：上游真挂 or 消费方误报 RETRYABLE_FAIL；逃生 = 上游 FEED 显式 `status:"ACTIVE"` + ping |
| resolve 全 EMPTY | 表 status / 条目全 OFFLINE / capacity 配置过紧（全满载）/ filter-script 全杀（临时摘除试） |
| 并发治理「失灵」 | 消费方是否漏发 report（租约回收数告警）；`conc_active` 与上游实际并发对账 |
| 亲和「失灵」 | 确认消费方没在本地缓存绑定（手册红线）；查 `affinity-events`（BIND/DETACH 史） |
| 日志超过 7 天的查询 | ring 只留热窗 7d，全量走结构化日志 → Loki（按 `[TR-RESOLVE]` marker 检索） |
