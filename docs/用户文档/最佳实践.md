# token-route 最佳实践

> 面向**消费方**与**表管理方**的经验准则：怎么做得稳，而不是怎么做（怎么做见 [01_消费方接入手册.md](./01_消费方接入手册.md)）。
> 每节独立可读；§1/§7 为接入清单强制项的展开。

## 1. 消费方：降级预案设计（接入强制项）

token-route 不可用 = 你没有路由可用。三选一（或组合），**接入前实现并演练**：

| 模式 | 做法 | 适合 |
|---|---|---|
| 本地兜底表 | 条目载荷静态配置在本地，按顺序轮询使用 | 上游集合稳定、变更低频 |
| 熔断直连 | 直连默认上游 + 本地熔断器保护 | 有一个公认的主上游 |
| 拒绝 | resolve 失败快速抛错，让上游调用方重试 | 调用方本身有重试/排队能力 |

- **组合建议**：本地兜底表打底 + 对兜底上游做熔断——兜底表也要防上游真挂；
- **演练要求**：接入验收时把 token-route 容器停一次，确认预案真的生效（多数团队跳过这步，故障时才发现预案是摆设）；
- resolve 客户端超时 1~3s 即可（服务端 P99 ≤ 20ms），超时等于不可用，立刻走预案，不要长等。

## 2. 消费方：report 批量与关停 flush

- 默认批量参数（满 100 条或 1s 刷一次）适配绝大多数场景；高 QPS 可调大 `report-batch-size`，不要为小批量牺牲吞吐；
- **优雅停机必做**：应用关停钩子里 flush 批缓冲。丢失尾部回填的后果是可控的但要知道：租约超时回收时**速率照计（保守）**、成功未被计入健康窗（上游「看起来更差一点」）；
- report 全链异步，任何情况下不要在业务主链路同步等 report——它是观测与治理信号，不是业务确认。

## 3. 消费方：亲和模式使用准则

- **该开**：任务轮询、多轮会话等「必须回同一上游」的场景（任务 ID 即天然 session）；
- **别开**：无状态请求——亲和对你没有收益，只付绑定维护成本；
- **session 粒度选任务级**，其次会话级；**禁用全局固定值**（全部请求黏死在单条目上，等于废掉路由）；
- **idle-timeout 与轮询间隔配比**：`idle-timeout ≥ 3 × 最大轮询间隔`（默认 8h 覆盖绝大多数任务）；长间隔低频任务注意会话空闲被脱离后下次 resolve 是 NEW——业务需容忍换条目；
- **立即 failover = detach → resolve**（单次失败后亲和仍黏着原条目，直接再 resolve 不会换）。

## 4. 消费方：failover 与重试纪律

- resolve 重试（EMPTY/超时后）用**退避 + 抖动**（如 500ms~2s 随机）：无退避的紧循环重试会把 EMPTY 放大成 resolve 风暴；
- `RETRYABLE_FAIL` 后立刻换条目（无亲和直接再 resolve；有亲和先 detach）还是等状态机自动摘除，取决于业务实时性——任务类建议立刻换，吞吐类可等降权；
- **上游调用超时要 < lease_ttl**（默认 30s）：调用耗时超过租约 TTL 期间并发位已被回收重用，容量治理失真；长耗时任务调大表级 `lease-ttl-seconds`。

## 5. 管理方：capacity 阈值设定

| 阈值 | 建议算法 | 说明 |
|---|---|---|
| `max_concurrency` | 上游可承受 QPS × 平均耗时(s) × 1.2 | Little's Law + 20% 余量；宁小勿大（大 = 治理形同虚设） |
| `rate_limit_value` / `rate_window_ms` | 按上游真实配额折算（如供应商 RPM/TPM） | 有硬配额必配；无配额可不配（仅状态机约束） |
| `lease-ttl-seconds`（表级） | ≥ 上游 P99 耗时 + 余量 | 默认 30s 适配常规调用；长任务显式调大 |
| `rate_unit` 口径 | TOKEN/BIT 表要求消费方如实回传 | 全传 1 = 限速口径失真，接入时核对（接入手册 §10 清单项） |

- capacity 整体缺省 = 该条目不受容量治理（仅状态机约束）——对无配额担忧的上游是合理默认；
- 阈值调整走上游 FEED 数据 + refresh ping，**下一请求即生效**，无需重启。

## 6. 管理方：脚本表使用准则

- 优先「内置四策略 + `filter_script`」组合；`selector_script`（集合级）留给真正需要集合决策的场景（如价格优先），别为过滤需求写选择器；
- 脚本保持纯函数、轻量——filter 逐条目求值，脚本表条目建议 ≤ 数百（配置手册 §3 规模指引）；
- 脚本以文件随部署制品版本化，变更 = 滚动重启；启动编译 fail-fast 保证坏脚本上不了线，评审脚本时关注**逻辑正确性**而非安全性（沙箱已在编译期兜底，05 号）。

## 7. 管理方：新消费方灰度接入

1. 先 `none` 模式内网接入，要求消费方带 `X-Caller-Id`，观测 SLI（EMPTY 率 / 租约超时回收数 / 401 率）一周；
2. 回收数持续 > 0 → 督促消费方修 report 漏发（这是接入质量的第一信号）；
3. 稳定后切 `apikey`（或 jwt）；切模式 = 改配置滚动重启，低峰操作；
4. 新表先 `WEIGHTED_RANDOM` 起步，观察状态机行为符合预期后再引入脚本。

## 8. 反模式清单（明确别做）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 本地缓存 session→entry 映射 | 服务端可能已重绑，缓存吐过期绑定 | 每次以 resolve 返回为准 |
| 用 resolve 当并发信号量/心跳 | 每次 resolve 都预占并发位，虚占额度 | 并发治理交给 lease + report，心跳用你自己的机制 |
| 一次 resolve 多个条目并行用 | 每个 lease 占一个并发额度，且状态机只知其一 | 一调用一 resolve 一 report |
| 把 `DISABLE_FAIL` 当业务开关用 | 立即全局 FROZEN，误伤其他消费方 | 只对持续性不可用使用；业务开关走上游 FEED status |
| 消费方直改 Redis 键 | 绕过 Lua 原子面，计数/状态漂移 | 一切经契约面；调数据走 FEED |
| 指望 token-route 做用户/key 限流 | 边界明确不做（对消费方的保护限流在网关侧） | 网关侧限流；token-route 只管条目容量 |
| 在 resolve 与 report 之间做超长处理（> lease_ttl） | 租约已超时回收，速率照计、并发被复用 | 长任务拆步上报或调大 lease-ttl |
